# /team-deploy — Safe Team Deployment Command

## Purpose

Safe deployment workflow for teams. Prevents direct commits to main, ensures sync, detects conflicts, and requires PR review.

---

## Rules (STRICT)

- NEVER commit directly to main
- ALWAYS create a feature branch before commit
- ALWAYS sync with main before starting
- NEVER auto-merge PR
- MUST detect conflicts BEFORE deployment
- STOP if no changes detected

---

## Steps

### 1. Pre-check: Ensure there are changes

Run:
git status

IF no changes:
STOP and output: "No changes to deploy."

---

### 2. Sync with latest main (SAFE REBASE)

Run:
git stash -u
git checkout main
git pull --rebase origin main

Then restore stashed changes:
git stash pop

IF `git stash pop` fails with a conflict:
STOP and output:

⚠️ STASH CONFLICT

Your local changes conflict with the latest main.

To fix manually:

1. `git stash show -p` — review stashed changes
2. Resolve conflicts in the affected files
3. `git stash drop` — remove the stash after resolving

Then re-run /team-deploy

---

### 3. Analyze changes

Detect changed areas:

- If files in `client/` → frontend
- If files in `server/` → backend
- If both → fullstack

---

### 4. Create branch (from updated main)

Branch name:
deploy/<short-description-or-timestamp>

Run:
git checkout -b deploy/<slug>

---

### 5. Commit changes

Stage only relevant files (NEVER use `git add .` or `git add -A`):
- If frontend changed: `git add client/`
- If backend changed: `git add server/`
- If docs changed: `git add docs/`
- If config files changed: add them individually

SAFETY CHECK before commit:
Run `git diff --cached --name-only` and verify:
- No `.env*` files are staged
- No `credentials.json`, `*.pem`, or secret files are staged
- IF any sensitive file is staged: `git reset HEAD <file>` and WARN the user

Then commit:
git commit -m "feat: deploy <description>"

---

### 6. Pre-push conflict check (LOCAL REBASE)

Before pushing, rebase on latest main to detect conflicts early:

Run:
git fetch origin main
git rebase origin/main

IF rebase fails with conflicts:
Run `git rebase --abort` to restore the branch, then STOP and output:

⚠️ CONFLICT DETECTED (before push)

Your branch conflicts with main. Fix locally:

1. `git rebase origin/main`
2. Resolve conflicts in the listed files
3. `git add <resolved-files>`
4. `git rebase --continue`

Then re-run /team-deploy

IF rebase succeeds: continue to next step.

---

### 7. Push branch

Run:
git push origin deploy/<slug>

---

### 8. Create DRAFT PR

Run:
gh pr create --draft --base main --head deploy/<slug> --title "Deploy: <description>" --body "Auto-generated by /team-deploy"

---

### 9. Deploy

IF frontend changed:
Deploy to Vercel

IF backend changed:
Deploy to Railway

IF both:
Deploy both

---

### 10. CORS check (if frontend domain changed)

IF deploying to a NEW Vercel preview URL or a new custom domain:

Check `server/src/main.ts` CORS origin list.
IF the new domain is NOT in the list:
WARN the user:

⚠️ CORS UPDATE NEEDED

New frontend domain detected. Add it to the CORS origin list in `server/src/main.ts`:

```typescript
app.enableCors({
  origin: [
    'http://localhost:3000',
    'https://client-brown-ten-36.vercel.app',
    'https://admin.dafzentrum.uz',
    'https://<NEW_DOMAIN>',  // ← add this
  ],
  credentials: true,
});
```

Then redeploy the backend.

---

### 11. Mark PR as Ready

Run:
gh pr ready

---

### 12. Cleanup

Run:
git checkout main

---

## Output

- PR link
- Deployment status (client/server)
- CORS warning (if applicable)
- Clear message: "Waiting for review (no auto-merge)"
